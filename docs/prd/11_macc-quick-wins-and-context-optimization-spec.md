# MACC Quick Wins and Context Optimization Specification

> **Project:** MACC — Multi-Assistant Code Config  
> **Document type:** Detailed implementation proposal / spec patch  
> **Language:** English  
> **Status:** Draft proposal  
> **Date:** 2026-05-27

---

## 1. Executive Summary

This proposal consolidates the recently discussed MACC improvements into a coherent, implementation-ready motif:

> **Operator signal-to-noise + context budget control.**

The goal is to make MACC easier to operate under real parallel workload, especially when many tasks, worktrees, assistants, and logs are active at the same time. The proposal combines two complementary improvement streams:

1. **Quick wins for coordinator and worktree usability**
   - `macc logs tail --task <id>` filters logs/events to a single task.
   - `macc worktree open <id>` prints the path when no launcher is available.
   - Coordinator heartbeat interval becomes configurable in `.macc/macc.yaml`.
   - Web UI status cards expose the last event message, not just the event type.
   - `macc tasks list` defaults to non-completed tasks, with `--all` for the complete view.

2. **Token and context optimization through tool-output summarization hooks**
   - MACC should summarize or filter noisy tool outputs before they enter model context.
   - Built-in hook bundles should cover test output, lint output, stack traces, git diffs, and logs.
   - Hook behavior should be configurable per tool and generated by `macc apply` through adapters.

Together, these changes make MACC more scalable for busy coordinator runs, CI usage, large task registries, and long-lived projects where raw logs and completed task history quickly become overwhelming.

---

## 2. Design Principles

### 2.1 Optimize for the operator's next question

MACC should answer the following questions quickly:

- What is happening with this task?
- Which tasks still need attention?
- Is the coordinator alive or stuck?
- What was the last meaningful event?
- Why did this tool fail?
- Which output matters, and which output is just noise?

### 2.2 Preserve raw data, compress display/context

MACC should not destroy diagnostic information. Raw logs, full test output, full diffs, and complete event streams should remain available on disk. However, default CLI output, Web UI cards, and AI context should prefer summarized, filtered, or task-scoped views.

### 2.3 Make graceful degradation a default behavior

Commands should not fail when MACC can still provide useful information. For example, if no terminal launcher is available, `macc worktree open <id>` should print the worktree path instead of returning a hard error.

### 2.4 Keep CLI, TUI, Web UI, and API behavior consistent

Any observability improvement should be reflected across:

- CLI commands;
- TUI coordinator screens;
- Web UI cards and streams;
- REST/SSE API contracts;
- event schema and log storage.

### 2.5 Make context optimization explicit and configurable

Tool-output summarization must be visible, predictable, and configurable. MACC should expose which summarizers are active and allow users to disable or tune them when they need full raw output.

---

## 3. Scope

### 3.1 In scope

This proposal covers:

- CLI behavior changes;
- coordinator configuration additions;
- event/log schema improvements;
- Web API additions;
- Web UI/TUI implications;
- token-budget hook architecture;
- built-in summarization/filtering bundles;
- acceptance criteria and phased implementation plan.

### 3.2 Out of scope

This proposal does not attempt to:

- replace the coordinator runtime;
- redesign the entire PRD/task registry model;
- introduce a remote hosted MACC service;
- execute remote hook code;
- store secrets or expose private logs externally.

## 4. Quick Win 1 — `macc logs tail --task <id>`

### 4.1 Problem

When the coordinator is busy, global logs become noisy. A single run may include:

- coordinator heartbeats;
- task dispatch events;
- performer progress;
- runner stdout/stderr;
- review phase results;
- retry/backoff events;
- merge attempts;
- cleanup events;
- rate-limit state changes.

The operator often wants a task-specific answer:

> “Show me only what happened to `TASK-042`.”

### 4.2 Proposed CLI behavior

```bash
macc logs tail
macc logs tail --task TASK-042
macc logs tail --task TASK-042 --events
macc logs tail --task TASK-042 --performer
macc logs tail --task TASK-042 --coordinator
macc logs tail --task TASK-042 --json
macc logs tail --task TASK-042 --since 10m
```

Default behavior remains global. Adding `--task <id>` narrows output to events and logs associated with that task.

### 4.3 Matching rules

MACC should match task IDs in this order:

1. **Structured fields**
   - `task_id`
   - `task.id`
   - `runtime.task_id`
   - `macc.task_id`

2. **Structured commit/task tags**
   - `[macc:task TASK-042]`

3. **Known MACC log prefixes**
   - `[TASK-042] ...`
   - `task=TASK-042 ...`

4. **Fallback text search**
   - only when no structured field exists.

Structured matches should always take precedence over text matching to avoid false positives.

### 4.4 Recommended event envelope

All coordinator and performer events should converge toward this shape:

```json
{
  "ts": "2026-05-27T10:14:03Z",
  "level": "info",
  "source": "coordinator",
  "event_type": "performer_heartbeat",
  "task_id": "TASK-042",
  "worktree_id": "worker-03",
  "tool": "codex",
  "phase": "dev",
  "message": "Dev phase still running; 3 files changed; last output 8s ago.",
  "raw_ref": ".macc/log/performer/worker-03.log:1842"
}
```

### 4.5 CLI output example

```text
10:14:03  TASK-042  performer_heartbeat  Dev phase still running; 3 files changed; last output 8s ago.
10:14:16  TASK-042  phase_result          Dev phase completed successfully.
10:14:19  TASK-042  review_started        Review phase started with claude.
```

### 4.6 Empty-state behavior

If a task exists but no live events are available:

```text
No live events found for TASK-042.

Recent registry state:
  state: in_progress
  runtime_status: dispatched
  worktree: worker-03

Try:
  macc logs show --task TASK-042
  macc tasks inspect TASK-042
```

If the task does not exist:

```text
Unknown task id: TASK-999

Try:
  macc tasks list --all
```

### 4.7 Web API alignment

Add task filtering to existing SSE endpoints:

```http
GET /api/v1/logs/tail?task_id=TASK-042
GET /api/v1/events?task_id=TASK-042
```

Optional additional filters:

```http
GET /api/v1/events?task_id=TASK-042&source=performer
GET /api/v1/events?task_id=TASK-042&phase=review
GET /api/v1/logs/tail?task_id=TASK-042&since=10m
```

### 4.8 Acceptance criteria

- `macc logs tail --task TASK-042` shows only events linked to `TASK-042`.
- Structured `task_id` matching is preferred over plain text matching.
- The command works for both coordinator and performer logs.
- `--json` emits machine-readable events.
- Unknown task IDs produce a clear, actionable error.
- Web SSE streams support the same task filter.

## 5. Quick Win 2 — Graceful `macc worktree open <id>` fallback

### 5.1 Problem

`macc worktree open <id>` may fail when no terminal/editor launcher is detected. But the most useful information is already known: the path.

Failing hard creates unnecessary friction, especially on:

- minimal Linux servers;
- CI containers;
- WSL environments;
- remote SSH sessions;
- machines without VS Code or a desktop terminal.

### 5.2 Proposed behavior

```bash
macc worktree open worker-03
```

If a launcher is found, MACC opens the worktree as usual.

If no launcher is found, MACC prints:

```text
No terminal or editor launcher found.

Worktree path:
.macc/worktree/worker-03

Open it manually:
cd .macc/worktree/worker-03
```

The command should exit successfully when the worktree exists and MACC printed a valid path.

### 5.3 New `--print-path` flag

```bash
macc worktree open worker-03 --print-path
```

Output:

```text
/mnt/project/.macc/worktree/worker-03
```

No extra text should be printed in this mode. This enables shell composition:

```bash
cd "$(macc worktree open worker-03 --print-path)"
```

### 5.4 Launcher resolution order

Suggested detection order:

1. explicit `--editor <cmd>`;
2. explicit `--terminal` launcher;
3. configured default in `.macc/macc.yaml`;
4. `$EDITOR`;
5. known editors: `code`, `cursor`, `windsurf`, `zed`;
6. known terminal launchers by OS;
7. fallback path print.

### 5.5 Exit code policy

| Case | Exit code | Behavior |
|---|---:|---|
| Worktree found and opened | `0` | Open normally |
| Worktree found, launcher missing | `0` | Print path and manual `cd` hint |
| `--print-path`, worktree found | `0` | Print only path |
| Unknown worktree id | non-zero | Print actionable error |
| Launcher configured but command fails | non-zero or fallback depending on flag | Prefer clear error plus path |

### 5.6 Acceptance criteria

- Missing launcher no longer blocks the user.
- `--print-path` is stable and script-friendly.
- Unknown worktree IDs still fail clearly.
- Existing `--editor` and `--terminal` behavior remains compatible.

## 6. Quick Win 3 — Configurable coordinator heartbeat interval

### 6.1 Problem

A fixed 30-second heartbeat is reasonable for local usage, but too slow for CI and near-real-time dashboards. In CI, users often need fast visibility into whether a task is alive, stalled, rate-limited, or blocked.

### 6.2 Proposed config

Add to `.macc/macc.yaml`:

```yaml
automation:
  coordinator:
    heartbeat_interval_seconds: 30
    heartbeat_stale_multiplier: 3
```

The stale threshold can be derived as:

```text
stale_after = heartbeat_interval_seconds * heartbeat_stale_multiplier
```

### 6.3 Example profiles

#### Local default

```yaml
automation:
  coordinator:
    heartbeat_interval_seconds: 30
    heartbeat_stale_multiplier: 3
```

#### CI profile

```yaml
automation:
  coordinator:
    heartbeat_interval_seconds: 5
    heartbeat_stale_multiplier: 4
```

#### Low-noise profile

```yaml
automation:
  coordinator:
    heartbeat_interval_seconds: 60
    heartbeat_stale_multiplier: 3
```

### 6.4 CLI and environment overrides

```bash
macc coordinator --heartbeat-interval-seconds 5
```

Optional environment variable:

```bash
MACC_COORDINATOR_HEARTBEAT_INTERVAL_SECONDS=5
```

Recommended precedence:

```text
CLI flag > environment variable > .macc/macc.yaml > built-in default
```

### 6.5 Validation bounds

Recommended bounds:

```text
minimum: 2 seconds
maximum: 300 seconds
default: 30 seconds
```

Invalid config should fail early:

```text
Invalid coordinator config:
heartbeat_interval_seconds must be between 2 and 300.
```

### 6.6 Important distinction

Heartbeat interval and stale policy are related but not identical:

- `heartbeat_interval_seconds` controls **visibility frequency**.
- stale thresholds control **failure detection and recovery policy**.

They should remain separate configuration concepts.

### 6.7 TUI/Web UI implications

The Automation Settings screen should expose:

- heartbeat interval;
- stale multiplier;
- effective stale-after duration;
- warning if CI-like interval may produce more log volume.

Example display:

```text
Heartbeat interval: 5s
Stale after: 20s
Mode: CI / high visibility
```

### 6.8 Acceptance criteria

- Coordinator emits heartbeat events at the configured interval.
- Existing projects behave unchanged when the setting is absent.
- CLI override works.
- Invalid values are rejected with clear errors.
- Web UI and TUI display the effective value.

## 7. Quick Win 4 — `/api/v1/status` should include last event message

### 7.1 Problem

A status card that only shows an event type is too vague:

```text
coordinator_heartbeat
```

The operator needs the meaningful message:

```text
Task TASK-042 still running; performer active; last output 8s ago.
```

### 7.2 Proposed API addition

Extend `GET /api/v1/status` with `last_event`:

```json
{
  "coordinator": {
    "state": "running",
    "active_workers": 3,
    "paused": false
  },
  "tasks": {
    "todo": 12,
    "in_progress": 3,
    "merged": 18,
    "failed": 1
  },
  "last_event": {
    "ts": "2026-05-27T10:14:03Z",
    "event_type": "coordinator_heartbeat",
    "level": "info",
    "task_id": "TASK-042",
    "worktree_id": "worker-03",
    "tool": "codex",
    "message": "Task TASK-042 still running; performer active; last output 8s ago."
  }
}
```

### 7.3 Optional active task summaries

For richer dashboards, add:

```json
{
  "active_task_summaries": [
    {
      "task_id": "TASK-042",
      "title": "Implement task-scoped log tailing",
      "state": "in_progress",
      "runtime_status": "running",
      "tool": "codex",
      "worktree_id": "worker-03",
      "last_event_type": "performer_heartbeat",
      "last_event_message": "3 files changed; tests not started yet.",
      "last_event_at": "2026-05-27T10:14:03Z"
    }
  ]
}
```

### 7.4 Web UI card behavior

A task card should show:

```text
TASK-042
Running · Codex · worker-03
3 files changed; tests not started yet.
Last event: 8s ago
```

A coordinator card should show:

```text
Coordinator running
3 active workers · 2 throttled tools
Last event: Reconciled registry; no stale tasks found.
```

### 7.5 Message safety rules

Before returning or displaying `message`, MACC should:

- strip ANSI escape sequences;
- redact likely secrets;
- normalize whitespace;
- truncate to a safe length, recommended 160-240 characters;
- preserve full raw log reference separately when available;
- fall back to `event_type` when no message exists.

### 7.6 Backward compatibility

This is an additive API change. Existing clients that only read `event_type`, task counts, or coordinator state continue to work.

### 7.7 Acceptance criteria

- `/api/v1/status` includes `last_event.message`.
- The Web UI displays meaningful event text in status cards.
- Messages are redacted and truncated.
- No breaking changes to existing status fields.

## 8. Quick Win 5 — `macc tasks list` defaults to non-done tasks

### 8.1 Problem

Task registries grow over time. If `macc tasks list` shows all completed tasks by default, the command becomes less useful with every successful run.

The default view should answer:

> “What still needs attention?”

### 8.2 Proposed default behavior

```bash
macc tasks list
```

Default output includes active/non-terminal states only:

- `todo`
- `claimed`
- `in_progress`
- `changes_requested`
- `queued`
- `pr_open`
- `failed`
- `blocked`
- `rate_limited`
- `stale`

Completed/terminal states are hidden by default:

- `merged`
- `done`
- `abandoned`
- `cancelled`
- `skipped`

### 8.3 Flags

```bash
macc tasks list --all
macc tasks list --done
macc tasks list --status in_progress
macc tasks list --status todo,blocked,failed
macc tasks list --limit 50
macc tasks list --json
```

### 8.4 Empty-state behavior

When no active tasks remain:

```text
No active tasks.

Completed tasks are hidden by default.
Run `macc tasks list --all` to include merged/done tasks.
```

### 8.5 JSON behavior

Recommended JSON output:

```json
{
  "filter": {
    "terminal_tasks_included": false,
    "states": ["todo", "claimed", "in_progress", "changes_requested", "queued", "pr_open", "failed", "blocked", "rate_limited", "stale"]
  },
  "counts": {
    "shown": 4,
    "hidden_terminal": 32
  },
  "tasks": []
}
```

### 8.6 Backward compatibility

This change can affect scripts. Recommended mitigation:

- announce the behavior change in release notes;
- keep `--all` as the explicit old behavior;
- include filter metadata in JSON;
- optionally support `MACC_TASKS_LIST_INCLUDE_DONE=true` for one transition release.

### 8.7 Acceptance criteria

- `macc tasks list` shows only active tasks by default.
- `macc tasks list --all` includes completed tasks.
- Empty state teaches the new behavior.
- JSON output includes filter metadata.

## 9. Previously Discussed Improvement — Summarize tool outputs before context ingestion

### 9.1 Problem

Tool output is one of the largest avoidable sources of context bloat. Common examples:

- test logs with thousands of passing lines;
- lint output with repeated file paths;
- stack traces with repeated framework internals;
- full git diffs when a diff stat would be enough first;
- application logs where only the first relevant error matters;
- CI logs that include install noise, progress bars, cache messages, and repeated warnings.

When these raw outputs enter the model context, they reduce reasoning capacity and increase cost without improving task quality.

### 9.2 Goal

MACC should introduce a **tool-output context filter pipeline** that can summarize, collapse, redact, or reorder noisy outputs before they are injected into AI assistant context.

Important distinction:

- raw output remains stored in `.macc/log/`;
- filtered output is what enters the model prompt or appears in compact UI summaries.

### 9.3 Proposed name

Recommended internal feature name:

```text
Context Filters
```

Alternative names:

- Tool Output Summarizers;
- Context Budget Hooks;
- Output Compaction Hooks;
- Signal Filters.

Recommended CLI terminology:

```bash
macc context-filters list
macc context-filters preview --tool codex --file .macc/log/performer/worker-03.log
```

## 10. Context Filter Pipeline

### 10.1 High-level flow

```text
Tool runs
  ↓
Raw stdout/stderr captured
  ↓
Raw logs stored under .macc/log/
  ↓
Context filter pipeline runs
  ↓
Filtered summary generated
  ↓
Summary enters assistant context / Web UI card / TUI compact view
```

### 10.2 Pipeline stages

Recommended stages:

1. **Capture**
   - collect stdout, stderr, exit code, duration, command, cwd, task ID, tool ID.

2. **Classify**
   - detect output type: test, lint, build, stacktrace, git diff, git status, generic log.

3. **Filter**
   - remove low-value lines and repeated noise.

4. **Summarize**
   - produce compact structured output.

5. **Redact**
   - remove likely secrets before display or context injection.

6. **Budget**
   - enforce token or character limits.

7. **Attach raw reference**
   - include a pointer to the full raw log file.

### 10.3 Filtered output envelope

```json
{
  "kind": "filtered_tool_output",
  "task_id": "TASK-042",
  "tool": "codex",
  "command": "pnpm test",
  "exit_code": 1,
  "raw_ref": ".macc/log/performer/worker-03/test-20260527-101403.log",
  "filter_bundle": "test-output-failures-only",
  "input_bytes": 842391,
  "output_bytes": 12840,
  "truncated": false,
  "summary": {
    "status": "failed",
    "failed_tests": 3,
    "passed_tests": 184,
    "first_failure": "TaskLogFilter should keep structured task_id metadata",
    "recommended_next_action": "Inspect src/logs/task_filter.rs and update the structured parser."
  },
  "content": "...compact markdown summary..."
}
```

## 11. Built-in Context Filter Bundles

MACC should ship with default bundles generated by `macc apply` where the target assistant supports hooks or equivalent configuration.

### 11.1 Bundle: `test-output-failures-only`

#### Purpose

Keep failed tests, assertion messages, failing file paths, and final summary. Remove passing test noise.

#### Input examples

- `pnpm test`
- `cargo test`
- `pytest`
- `vitest`
- `jest`
- `playwright test`

#### Output should include

- command;
- exit code;
- test framework if detected;
- count of passed/failed/skipped tests;
- failing test names;
- assertion messages;
- relevant file paths and line numbers;
- shortest useful stack trace;
- raw log reference.

#### Example output

```markdown
## Test Summary

Command: `pnpm test`
Status: failed
Passed: 184
Failed: 3

### First failure

`TaskLogFilter keeps structured task_id metadata`

File: `src/logs/task_filter.test.ts:42`

Expected `TASK-042`, received `null`.

### Recommended next step

Check the JSON event parser before fallback text matching.

Full output: `.macc/log/performer/worker-03/test-20260527-101403.log`
```

### 11.2 Bundle: `lint-errors-only`

#### Purpose

Keep only lint errors and high-confidence warnings. Remove formatting noise and repeated rule documentation.

#### Output should include

- file path;
- line/column;
- rule ID;
- message;
- fixability;
- total error/warning count.

#### Example output

```markdown
## Lint Summary

Status: failed
Errors: 4
Warnings: 2

| File | Line | Rule | Message |
|---|---:|---|---|
| `src/web/status.ts` | 88 | `no-explicit-any` | Replace `any` with a typed status envelope. |
| `src/logs/filter.rs` | 131 | `clippy::collapsible_if` | Collapse nested if statements. |

Full output: `.macc/log/performer/worker-03/lint-20260527-101455.log`
```

### 11.3 Bundle: `stacktrace-collapse`

#### Purpose

Collapse long stack traces while preserving the frames that matter.

#### Rules

Keep:

- top application frame;
- direct call site;
- root cause message;
- file and line numbers;
- caused-by chain;
- panic/assertion text.

Collapse:

- repeated framework internals;
- dependency frames;
- async runtime boilerplate;
- repeated identical frames.

#### Example output

```markdown
## Error Summary

Error: `InvalidTaskFilter: task_id cannot be empty`

Relevant frames:

1. `src/logs/task_filter.rs:44` — validates task filter input
2. `src/cli/logs.rs:92` — builds log tail request
3. `src/main.rs:41` — CLI dispatch

Collapsed 47 framework/runtime frames.

Full stack trace: `.macc/log/performer/worker-03/error-20260527-101503.log`
```

### 11.4 Bundle: `git-diff-stat-before-full-diff`

#### Purpose

Avoid injecting full diffs immediately. Start with diff stat and changed-file summary. Escalate to full diff only when needed.

#### Output should include

- changed files;
- insertions/deletions;
- high-risk files;
- generated files excluded by default;
- recommendation whether full diff is needed.

#### Example output

```markdown
## Diff Summary

Changed files: 6
Insertions: 214
Deletions: 48

| File | Change | Notes |
|---|---:|---|
| `core/src/logs/task_filter.rs` | +92 / -10 | Adds structured task-id filter. |
| `cli/src/commands/logs.rs` | +44 / -8 | Adds `--task` option. |
| `web/src/api/status.ts` | +31 / -4 | Adds `last_event.message`. |

Potential risk:
- API response shape changed. Confirm backward compatibility.

Full diff available on request.
```

### 11.5 Bundle: `log-grep-error-first`

#### Purpose

For generic logs, surface errors and warnings before full chronological output.

#### Priority order

1. fatal errors;
2. explicit `ERROR` lines;
3. failed command summaries;
4. warnings;
5. timeout/rate-limit messages;
6. final status lines;
7. raw tail excerpt.

#### Example output

```markdown
## Log Summary

Detected errors: 2
Detected warnings: 5

### First error

`ERROR task=TASK-042 failed to parse event envelope: missing task_id`

### Last relevant lines

- Coordinator continued running.
- Task was marked `failed`.
- Retry is eligible under E103 policy.

Full log: `.macc/log/coordinator/run-20260527.log`
```

## 12. Context Filter Configuration

### 12.1 Proposed `.macc/macc.yaml` shape

```yaml
automation:
  context_filters:
    enabled: true
    default_token_budget: 3000
    preserve_raw_logs: true
    redact_secrets: true
    bundles:
      - test-output-failures-only
      - lint-errors-only
      - stacktrace-collapse
      - git-diff-stat-before-full-diff
      - log-grep-error-first
```

### 12.2 Per-tool configuration

```yaml
tools:
  codex:
    enabled: true
    context_filters:
      enabled: true
      token_budget: 2500
      bundles:
        test: test-output-failures-only
        lint: lint-errors-only
        stacktrace: stacktrace-collapse
        diff: git-diff-stat-before-full-diff
        logs: log-grep-error-first

  claude:
    enabled: true
    context_filters:
      enabled: true
      token_budget: 3500
      adapter_mode: hooks

  gemini:
    enabled: true
    context_filters:
      enabled: true
      token_budget: 3000
      adapter_mode: summarize_tool_output
```

### 12.3 Per-command override

```yaml
automation:
  context_filters:
    commands:
      "pnpm test":
        bundle: test-output-failures-only
        token_budget: 4000
      "pnpm lint":
        bundle: lint-errors-only
        token_budget: 2000
      "git diff":
        bundle: git-diff-stat-before-full-diff
        token_budget: 2500
```

### 12.4 CLI overrides

```bash
macc coordinator --no-context-filters
macc coordinator --context-filter-budget 5000
macc logs show --raw --task TASK-042
macc logs show --filtered --task TASK-042
macc context-filters preview --bundle test-output-failures-only --file ./test.log
```

### 12.5 Control hierarchy

```text
CLI flag > per-tool config > command-specific config > global context_filters config > built-in default
```

## 13. Adapter Generation Through `macc apply`

### 13.1 Rationale

MACC already uses adapters to generate tool-specific files from a canonical source of truth. Context filters should follow the same model.

### 13.2 Adapter responsibilities

Each tool adapter should declare:

- whether it supports pre-context hooks;
- whether it supports post-tool-output summarization;
- where hook/config files should be written;
- how to express token budgets;
- whether output can be replaced or only annotated;
- how to preserve raw logs.

### 13.3 Conceptual adapter capability model

```rust
pub struct ToolContextFilterCapabilities {
    pub supports_pre_context_filter: bool,
    pub supports_post_tool_output_filter: bool,
    pub supports_replace_output: bool,
    pub supports_annotate_output: bool,
    pub supports_token_budget: bool,
    pub supports_per_command_rules: bool,
}
```

### 13.4 Generated files

Examples of generated files may include:

```text
.macc/generated/context-filters/test-output-failures-only.json
.macc/generated/context-filters/lint-errors-only.json
.tool/hooks/context-filter.yaml
.tool/settings/context-budget.json
```

Exact paths should remain adapter-specific.

### 13.5 Safety rule

Generated filters must be data/config only. MACC should not fetch or execute arbitrary remote hook code as part of this feature.

## 14. Raw Log Preservation and Redaction

### 14.1 Preserve raw logs

Raw logs should remain available under existing MACC log locations, for example:

```text
.macc/log/coordinator/
.macc/log/performer/
.macc/log/context-filter/
```

### 14.2 Store filtered outputs separately

Suggested location:

```text
.macc/log/context-filter/<task-id>/<timestamp>-<bundle>.md
.macc/log/context-filter/<task-id>/<timestamp>-<bundle>.json
```

### 14.3 Redaction requirements

Before any filtered output enters model context or Web UI cards, MACC should redact likely:

- API keys;
- bearer tokens;
- private keys;
- passwords;
- `.env` values;
- session tokens;
- cloud credentials;
- database URLs with credentials.

### 14.4 Redaction placeholder

```text
[REDACTED:possible_secret]
```

### 14.5 Acceptance criteria

- Full raw output remains accessible.
- Filtered output references the raw log path.
- Likely secrets are redacted before display/context injection.
- Redaction does not modify the raw log file unless explicitly requested by a separate cleanup command.

## 30. Strategic Outcome

After these changes, MACC will behave less like a raw orchestration log emitter and more like an operator-grade control plane.

The key UX shift is:

> From “show me everything that happened” to “show me what matters for this task, right now.”

The key token-efficiency shift is:

> From “put raw tool output into context” to “preserve raw output, but inject only the smallest useful summary.”

This is aligned with MACC's broader goals: consistent multi-tool configuration, safe automation, parallel worktree orchestration, local Web UI observability, and high-quality developer experience across machines and projects.
